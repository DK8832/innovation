# 데이터 출처 설계 — 왜 이렇게 만들었는가

이 문서는 "어떻게 만들었는가"보다 **"왜 다른 방법을 버렸는가"**를 남기기 위한 것입니다.
아래 결론은 전부 추측이 아니라 **직접 두드려본 실측**에서 나왔습니다 (확인 시점: 2026-08-15).

---

## 1. 처음 세운 가설과, 그것이 뒤집힌 과정

처음 계획은 흔히 알려진 방식대로였습니다.

> 수십 개 주관처 사이트의 공지사항과 시험 일정을 주기적으로 크롤링해 DB를 자동 갱신한다.

**실제로 두드려보니 이 전제가 틀렸습니다.**

| 대상 | 실측 결과 | 판정 |
|---|---|---|
| **큐넷** 연간 시험일정 페이지 | HTTP 200, 235KB 수신. 그러나 본문에 날짜가 없고 `viewStr += "<td>..."` 형태로 **JS가 표를 조립** | ❌ 정적 크롤링 불가 |
| **한국사능력검정시험** 시험일정 페이지 | HTTP 200이지만 본문 3.6KB, 내용은 `"오류발생 알림화면(허용되지 않는 요청을 하셨습니다)"` | ❌ **봇 차단** |
| **공공데이터포털** `apis.data.go.kr/B490007/qualExamSchd` | HTTP 403 + `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` → **엔드포인트 도달 성공, 키만 있으면 동작** | ✅ 채택 |

즉 크롤링은 "만들 수는 있지만 조용히 빈 값을 가져오는" 경로였습니다.
날짜가 틀리면 수험생이 시험을 통째로 놓치는 서비스에서, 조용히 실패하는 수집기는
없느니만 못합니다.

> **그래서 크롤링을 주 경로에서 내리고 공공 API를 1순위로 올렸습니다.**
> 이건 기능을 줄인 게 아니라, 실측에 맞춰 **더 정확한 출처로 갈아탄 것**입니다.

## 2. 확정된 구조

```
[공공데이터 API]  ──(키 있을 때만)──┐
   data.go.kr / 한국산업인력공단      │
                                    ├─→ 정규화 → 변경 감지 → 검토 큐 → (사람 확인) → exams.json
[큐레이션 데이터]  ──(항상 동작)────┘
   공식 사이트 직접 확인

[모집요강 원문] ─→ 날짜: 정규식 전용 ────────────┐
                └→ 서술형: 규칙 기반 → LLM 보강 ─┴─→ 원문 대조 통과분만 채택
```

### 지키는 규칙 세 가지

**① API 키가 없어도 서비스는 완전히 동작한다**

큐레이션된 `exams.json`이 항상 기본값이고, 공공 API는 그것을 갱신·대조하는 보조 수단입니다.
키가 없으면 화면의 데이터 출처 카드에 **"미설정"이라고 그대로 표시**합니다.
꺼진 기능을 켜진 것처럼 보이게 하지 않습니다.

**② 수집한 값을 자동으로 반영하지 않는다**

`sync_sources.py`는 `exams.json`을 **절대 수정하지 않습니다.** 기존 값과 다른 것만
`backend/data/review_queue.json`에 쌓고, 사람이 확인한 뒤 반영합니다.

자동 반영이 편하지만, 잘못된 날짜 하나가 사용자의 1년을 날릴 수 있는 도메인이라
"틀릴 수 있는 자동화"보다 "느리지만 확인된 갱신"을 택했습니다.

**③ 날짜는 절대 생성형 모델을 거치지 않는다**

`summarizer.py`에서 날짜는 정규식으로만 추출합니다. LLM에는 날짜를 요청하지도, 받지도 않습니다.
LLM은 응시자격·시험과목·합격기준 같은 **서술형 항목만** 다듬습니다.

그리고 LLM이 낸 값도 그대로 믿지 않고 **원문 대조(grounding)** 를 거칩니다.
추출값의 의미 토큰 중 70% 미만만 원문에 존재하면 지어낸 것으로 보고 폐기한 뒤,
규칙 기반 결과로 되돌립니다. 폐기된 항목은 화면에 그 사실을 표시합니다.

실측 (`grounding_ratio`):

| 후보 | 원문 근거 비율 | 채택 |
|---|---|---|
| 원문에 있는 내용 | 1.00 | ✅ |
| 절반만 진짜 | 0.33 | ❌ |
| 완전히 지어낸 내용 | 0.00 | ❌ |

## 3. 공공 API 상세

- **엔드포인트**: `http://apis.data.go.kr/B490007/qualExamSchd/getQualExamSchdList`
- **문서**: <https://www.data.go.kr/data/15074408/openapi.do>
- **키 넣는 곳**: 환경변수 `DATA_GO_KR_KEY` 또는 저장소 루트 `data_go_kr_key.txt` 첫 줄
  (두 경로 모두 `.gitignore`에 등록되어 있습니다)

응답 필드가 우리 스키마와 1:1로 대응됩니다.

| API 필드 | 우리 필드 | |
|---|---|---|
| `docRegStartDt` / `pracRegStartDt` | `apply_start` | 필기 / 실기 |
| `docRegEndDt` / `pracRegEndDt` | `apply_end` | |
| `docExamStartDt` / `pracExamStartDt` | `exam_start` | |
| `docExamEndDt` / `pracExamEndDt` | `exam_end` | |
| `docPassDt` / `pracPassDt` | `result_date` | |

### ⚠️ 아직 실측하지 못한 것 (정직하게 밝힙니다)

발급받은 API 키가 없어 **실제 응답 본문의 필드명을 눈으로 확인하지는 못했습니다.**
위 매핑은 공식 문서 기준이며, 종목명 필드는 문서마다 표기가 달라
`jmNm`, `jmfldnm`, `seriesNm` 등 후보를 순서대로 시도하도록 방어적으로 구현했습니다.

키를 발급받은 뒤 아래 명령으로 실제 스키마를 바로 확인할 수 있습니다.

```bash
python sync_sources.py --show-schema
```

파이프라인 자체(정규화 → 변경 감지)는 문서 스키마 그대로의 **가짜 응답을 주입해 검증**했고,
`verify_all.py`에 회귀 검사로 남겨두었습니다.

## 4. 종목 매칭을 일부러 보수적으로 둔 이유

API의 종목명과 우리 종목을 잇는 `match_exam()`은 **정확히 같거나 한쪽이 다른 쪽으로
시작할 때만** 매칭하고, 후보가 둘 이상이면 아예 매칭하지 않습니다.

느슨하게 맞추면 "전기기사"와 "전기공사기사"처럼 이름이 비슷한 다른 종목의 날짜를
가져다 붙이게 됩니다. 못 찾는 것보다 잘못 붙이는 쪽이 훨씬 위험합니다.
